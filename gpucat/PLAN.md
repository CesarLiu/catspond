# 在 GPUDrive 上跑 CAT 的实验（分支 `gpudrive-ppo`）

**目标：** MetaDrive 上的一个训练要 14–19 小时，而且 GPU 基本闲着。把 CAT 的设定搬到 GPUDrive（Madrona，几百个世界在 GPU 上并行），用 PPO 训练，以便：
- 每个设置跑 5–10 个种子；
- 补齐消融实验；
- 在第二个模拟器上复现 MetaDrive 的结论。

MetaDrive 的结果仍然是忠实复现 CAT 的主线；这里的结果换了观测、动力学和算法，不能直接和 CAT 论文或 MetaDrive 的结果比较。

**环境：** GPUDrive 装在 `~/gpudrive`，安装和编译过程见 `responsibility/GPUDRIVE_NOTES.md`。运行方式：

```bash
PYTHONPATH=~/gpudrive/build:~/gpudrive LD_LIBRARY_PATH=~/cuda-12.4/lib64 ~/gpudrive/.venv/bin/python -m scripts.gpucat.<脚本>
```

场景导出（`scripts/gpucat/export_scenes.py`）在本仓库的 Python 3.9 环境里跑。

## M0 的结果（`scripts/gpucat/m0_feasibility.py`，测试场景 400–463，`logs/gpucat/m0.json`）

**场景：** `gpucat/scenes.py` 和 `scripts/gpucat/export_scenes.py` 导出了 500 个场景，在 `logs/gpucat/scenes`：
- 物体的顺序是自车、对手，其余按离自车的距离排；
- 除自车以外全部标为专家，按日志回放；
- 对手的终点挪到 5 km 外，否则 GPUDrive 会在它接近日志里的终点时把它移走。

GPUDrive 每个世界最多 64 个智能体，有 161 个场景超过这个数，离自车最远的被丢掉。

| 检查 | 结果 |
|---|---|
| 只控制自车 | 64/64 个世界正好控制 1 个智能体，而且就是自车（按轨迹 id 核对） |
| 找到对手 | 64/64。默认的 `all_non_trivial` 只创建第 0 步就有效的智能体，会漏掉 7 个晚出现的对手（第 1–10 步出现），要用 `init_mode="all_objects"` |
| 运行时注入对手计划 | 把计划写进 `expert_trajectory_tensor`（零拷贝的 GPU 张量）。对手出现之前的步保留原数据，有效标志设为 0。回放和计划完全一致（误差 0.0 m），晚一步：第 k 步之后对手在计划的第 k−1 行，和 CAT 在 MetaDrive 里一样 |
| 自车按专家动作回放（delta_local） | 到达终点之前，误差最大 3 mm |
| 单独重置一半世界 | 写入的计划保留；被重置的对手回到计划的第一行（误差 0.0 m）；其他 32 个世界完全不动 |
| 碰撞 | GPUDrive 报 43/64 次；离线用三圆近似算是 62 次，用实际大小的矩形算是 60 次。原因是 GPUDrive 把车辆的碰撞框长宽都乘了 0.7（`src/consts.hpp:25` 的 `vehicleLengthScale`）。离线用 0.7 倍的矩形重算，也是 43 次，53/64 个世界的第一次碰撞步数完全相同，其余基本只差 1 步 |

**吞吐量（L4；带一个 PPO 规模的网络，actor 和 critic 各两层 256 单元；观测 2,984 维；另有 1 个 MetaDrive 训练在跑）：**

| 世界数 | 每秒世界步 | 显存 |
|---|---|---|
| 64 | 974 | 8.2 GB |
| 128 | 1,625 | 10.8 GB |
| 256 | 2,352 | 15.9 GB |
| 384 | 3,085 | 20.9 GB |

按 256 个世界算，100 万步的仿真约 7 分钟；MetaDrive 上一个 100 万步的训练要 14–19 小时。

**决定：碰撞框的缩放（2026-10-07）。** GPUDrive 默认把车辆碰撞框缩到 0.7 倍，是为了减少 WOMD 标注框带来的误报，但这让碰撞比 MetaDrive 和离线分析宽松（测试场景里 43 对 60 次）。

我们**不改 GPUDrive**，自车的碰撞在 torch 里自己判断：每一步用实际大小的矩形（分离轴检测）检查自车和其他所有车辆。这样做的理由：
- 我们用的是 `collision_behavior="ignore"`，碰撞只是一个标志、不影响运动，所以自己判断和模拟器内部判断在效果上等价；
- GPUDrive 的数据、基准和预训练策略都保持可用；
- 奖励和回合终止用实际大小，和 CAT/MetaDrive 一致；GPUDrive 原生的 0.7 倍判断也照样记录，两种都可以报告。

出界的判断同样受缩放影响，在 M2 写奖励时一起处理。

## M1 的结果（`gpucat/adversary.py`）

**为什么能预先计算。** CAT 的 `AdvGenerator.generate` 每个对抗回合都跑一次 DenseTNT，但输入只来自场景日志的前 11 步，每个场景只解析一次（`before_episode` 里的 `_parse`）。所以同一个场景每次得到的 32 条候选都一样。闭环只体现在打分上：用自车在这个场景里最近 5 条实际轨迹给候选算碰撞概率。

公平对手要用的对手运动集合（40 个采样）和自车运动集合（用来算可避免性），也只取决于日志，而且种子就是场景编号。所以这些量都能每个场景只算一次（`scripts/gpucat/precompute_candidates.py`，500 个场景约 4 分钟，`logs/gpucat/candidates.npz`）。每个回合要做的，只剩下用自车最近的轨迹打分和选择，这部分用 torch 在所有世界上批量完成。

**和 CAT 的一致性**（`scripts/gpucat/verify_selection.py`，全部 500 个场景，对照 `responsibility/adversarial.py` 的 numpy 实现；那份实现在第 6 步已经和 CAT 原版逐场景核对过，500/500）：

| 情形 | CAT 规则 | 公平规则（τ = 2 m，ρ = 0.1） |
|---|---|---|
| 只有日志路线（训练开始前） | 499/500 | 499/500 |
| 每个场景 5 条模拟的自车历史（变速 ×0.5–1.3、横向偏移 ±1.5 m、提前结束 10–80 步、概率不等） | 500/500 | 500/500 |

- **其他量：** β 的最大差 1.5e-6 m（日志路线）和 6.9e-4 m（模拟历史）；生成的对手计划差 2e-15。
- **唯一不一致的场景 434：** CAT 用 float32 的候选算 `arctan2`，torch 用 float64，朝向相差约 1e-7 弧度，两条候选的分数又几乎相同，选择就翻转了。在 float32 下改用 torch 的 `arctan2` 也复现不了 numpy 的结果，所以不再追求逐位一致。
- **训练时用 float32：** 在模拟历史上，CAT 规则一致的是 497/500。

**调试中发现的一个陷阱：** `x[mask, :n]` 里的 `mask` 是二维布尔掩码时，后面的切片 `:n` 并不作用在时间维上，取出来的仍是完整的 80 步。结果自车轨迹的朝向是在补零后的轨迹上算的，在模拟历史上只有 36/40 一致。改用整数下标后解决，并加了回归测试。

**速度。** 候选的朝向在加载时算好，自车轨迹的朝向在存入历史时算好。之后，256 个世界一次算完 CAT 打分、β 和公平选择只要 15 ms（不缓存时是 396 ms，基本都是 Python 循环）。

**测试：** `tests/responsibility/test_gpucat_adversary.py` 有 4 个测试：朝向在 ±π 附近与 CAT 一致；自车轨迹长短不一时打分一致；公平规则在 200 组随机输入上一致；生成的对手计划一致。

## M2：环境和 PPO（`gpucat/env.py`、`gpucat/ppo.py`、`scripts/gpucat/train.py`）

**决定（2026-10-07）：** 奖励仿照 MetaDrive，但碰撞后直接结束回合；出界用 MetaDrive 的判据，在 torch 里用实际大小的车身判断。

**照着 MetaDrive 的 ScenarioEnv（CAT 的配置）：**

| 项 | MetaDrive | 这里 |
|---|---|---|
| 每步奖励 | `driving_reward` × 沿当前车道前进的距离 | 沿自车路线（日志路径，延长 100 m）前进的弧长 |
| 到达 | 路线完成度 > 0.95，奖励 +10 | 同样；GPUDrive 判自车到达终点也算 |
| 出界 | 离路线 > 10 m、压到连续黄线、碰到"人行道"（`relax_out_of_road_done`），奖励 −10，回合结束 | 同样三条，见下 |
| 碰撞 | 每接触一步 −1，回合继续（`crash_vehicle_done=False`） | −1，**回合结束**（决定） |
| 静止车辆 | 不生成（`no_static_vehicles`；位置标准差 ≤ 3 m 的车辆） | 导出时同样去掉（自车和对手除外），每个场景的物体数中位数降到 11 |
| 动力学 | MetaDrive 物理引擎 | GPUDrive 的可逆自行车模型：加速度 [−6, 4] m/s²，曲率 ±0.3 /m |

**出界的三条判据，都是从 MetaDrive 源码核对的：**
- **人行道：** `ScenarioBlock` 把**所有**路沿（`is_road_edge`：外侧边界和中央隔离带）做成 0.2 m 宽、名为 `BOUNDARY_LINE` 的方块，车身碰到就算 `crash_sidewalk`。这里用路沿线段和实际大小的车身判断（`gpucat/geometry.py`）。
- **连续黄线：** `ScenarioBlock` 把每条非虚线的黄线（单黄实线、双黄实线、一侧虚线的双黄线）都做成名为 `LINE_SOLID_SINGLE_YELLOW` 的连续线。这里同样取这三种。
- **离路线 > 10 m。**

线段只保留离路线 20 m 以内的：每个场景路沿最多 2,432 段（中位数 952），黄线最多 1,272 段（中位数 201）。

**MetaDrive 的一条过滤没有照搬：** 车辆出现时如果和自车当前位置重叠，就不生成。这是运行时动态判断的，离线无法精确复现。

**日志上的误报。** 用日志里的自车（日志尺寸），500 个场景中：
- 碰到路沿的有 3 个场景；
- 碰到黄线的有 15 个，其中 11 个是双黄实线；用 MetaDrive 的自车尺寸 4.51×1.85 时是 6 个。

**环境检查**（`scripts/gpucat/check_env.py`，测试场景 400–499；检查时把自车临时切成专家，由 GPUDrive 精确回放日志）：
- **无对手：** 96 个到达，4 个误判出界（路沿 1 个、黄线 3 个），0 个碰撞；回放偏差 0 m。
- **CAT 对手，自车不躲避：** 89/100 碰撞（离线三圆近似是 94 次，碰撞步数中位数晚 2 步）。MetaDrive 的回放参照是 83%。
- **用 GPUDrive 的逆自行车动作回放：** 偏差中位数 0.34 m，到回合结束时 8.2 m，所以不能用这种方式检查误报。

**速度（每个世界独立自动重置）：**

| | 128 个世界 | 192 个世界 |
|---|---|---|
| 环境本身（随机动作，含全部判据） | 每秒 1,345 世界步，13.3 GB | 每秒 1,804 世界步，17.0 GB |
| 换一批场景 | 7.8 s | 11.8 s |
| 训练（含 PPO 更新） | 每秒约 585 个样本 | – |

和 M0 相比显存更大，因为用了 `all_objects`（晚出现的车辆也要创建）。256 个世界在 L4 上显存不够。

**开发中修掉的问题：**
1. **按回合同步：** 早期大部分回合很快就出界，结束的世界要空转到最慢的那个回合结束，每秒只有约 160 个有效样本。改成每个世界独立自动重置后，约 585 个。
2. **观测的显存泄漏：** `get_obs()[:, 0]` 是整块 `[W, 64, D]` 张量上的视图，rollout 每存一步，就让整块张量（128 个世界时 98 MB）一直留在显存里。改用 `get_obs(mask)`。
3. **Madrona 一个进程只能有一个模拟器：** 第二次创建会报 `setCudaHeapSize` 错误，所以检查脚本的速度测试单独开一个进程。

**第一次训练（replay_s0，2026-10-08）：** PPO，replay 模式，128 个世界，horizon 64，每 20 次迭代换一批场景。计划跑 5M 步；服务器要关机，在 4.59M 步停掉。`logs/gpucat/runs/replay_s0` 里的 model.pt 是 4.5M 步（第 550 次迭代）时保存的。

测试场景 400–499，无对手，确定性动作：

| 步数 | 到达 | 出界 | 碰撞 | 路线完成度 |
|---|---|---|---|---|
| 0.4M | 0.03 | 0.36 | 0.23 | 0.26 |
| 1.6M | 0.10 | 0.65 | 0.20 | 0.40 |
| 3.3M | 0.11 | 0.67 | 0.19 | 0.45 |
| 4.5M | 0.21 | 0.51 | 0.24 | 0.51 |

它在学，但很慢：3M 步以前几乎不动，之后才开始上升。作为对照，MetaDrive 上 TD3 replay 训练 1M 步，到达率 48%，路线完成度 70%。主要的失败是出界。

**原因（读代码得出，未用实验验证）：** 策略看不到决定出界的东西。
- GPUDrive 的观测（2,984 维：自车 6 维，63 个其他车辆各 6 维，200 个道路点各 13 维）把所有车道线都标成 `RoadLine`，不分颜色。压到连续黄线就出界，压到白虚线不会，策略却分不出这两种线。
- 关于路线，观测里只有终点的相对位置。MetaDrive 给 CAT 的策略的是沿路线的导航点，以及到路边和实线的侧向探测距离。

**修复（`gpucat/env.py` 的 `navigation`，默认开启）：** 在 GPUDrive 的观测后面追加 60 维，都用我们自己判出界时用的同一份路线和线段数据：
- 沿路线前方 5、10、20、30、50 m 的点，在自车坐标系下，除以 50 m；
- 到路线的距离（除以 10 m）和路线完成度；
- 24 条射线（每 15°）到路沿的距离，和到连续黄线的距离，各自单独一组，除以 50 m。

这些在 `tests/responsibility/test_gpucat_geometry.py` 和 `test_gpucat_navigation.py` 里有测试。旧模型仍可以用 `navigation=False` 加载，`scripts/gpucat/diagnose_outcomes.py` 会按运行的 config.json 自动选择。

## M3 之前：fair 对手的 β_j 和可避免性是否有效（`scripts/gpucat/verify_fair_validity.py`，2026-10-08）

**实现层面：** M1 已核对过，GPU 版和 numpy 版逐场景一致。这次按原流程重新生成，fair 的选择和 bank 里存的一致 499/500。

**有效性问题：** β_j 用的对手 40 条备选和可避免性用的自车 40 条采样，都是 DenseTNT 的原始采样，没有经过责任指标的有效性过滤（`responsibility/motion_filter.py`）。这里用两套过滤后重新选择：
- **对手：** `--valid-counterfactuals` 的规则，即路线车道、可行驶区域 3 m、运动学、不穿过第三辆车（自车除外）；
- **自车：** 可行驶区域 3 m 和运动学，因为换一条路线躲开也是有效的躲避。

两套过滤都只取决于场景，可以预先算好。

| | 日志路线（训练开始前） | 每个场景 5 条模拟历史 |
|---|---|---|
| fair 的选择不变 | 433/500（87%） | 476/500（95%） |
| 原来的选择在过滤后不合格 | 34（因 β 不合格 28 个，因可避免性不合格 7 个） | 16（β 9 个，可避免性 7 个） |
| 选中的候选会碰撞 | 原始 127 / 过滤 129 | 原始 339 / 过滤 337 |
| 同时通过两条测试的候选数（中位数） | 23 / 23 | 27 / 27 |

- **过滤保留的采样：** 对手的中位数 36/40，有 26 个场景少于 10 条；自车的中位数 40/40。
- **因 β 被拒的候选：** 原始 β 都在 1.0–2.0 m，刚好低于 τ = 2 m；过滤后升到 2.0–3.9 m。原因是原始采样里混进了别的意图的备选（比如本来直行、却拐向自车的采样），它们也离自车很近，于是把候选衬托得"不算有责任"。
- **两套过滤下 β 的中位变化是 0：** 大多数场景不受影响，影响集中在 β 接近阈值的少数场景。

**结论：** β_j 的计算本身正确，在大多数场景上对有效性过滤也稳健。但在 5–13% 的场景里，fair 的选择依赖于无效的备选。

**决定（2026-10-08）：两个版本都训练。**
- 先跑原版 fair（fair_nav_s0），它和 MetaDrive 的 `cat_fair2_0.1` 完全相同，用来检验结论能否复现；
- 再跑 fair_valid（fair_valid_nav_s0）：β 只在对手的有效备选上取 CVaR，可避免性只用自车的有效采样。

**fair_valid 的实现：**
- `scripts/gpucat/precompute_valid.py` 为每个场景预先算好对手有效采样的掩码，以及按有效自车采样算的可避免性，写到 `logs/gpucat/valid_samples.npz`。500 个场景约 15 分钟；对手采样保留的中位数是 36/40，最少 1 条。
- `gpucat/adversary.py` 的 `adversary_beta(..., sample_mask)` 只在掩码保留的采样上取 CVaR。
- 训练用 `--mode fair_valid`。

**核对：**
- 在 GPU 上用日志路线算的选择，和 numpy 过滤后的选择一致 500/500；和原版 fair 有 67 个场景不同。
- 测试 `test_beta_on_valid_samples_matches_numpy_on_the_subset` 覆盖掩码版 β。
- 8 个世界的冒烟训练正常。

**排队：** `logs/gpucat/queue_m3.sh` 等 cat_nav_s0 结束后，依次训练 fair_nav_s0 和 fair_valid_nav_s0，设置都相同（种子 0，5M 步，128 个世界）。

## M3 的结果（2026-10-09，每种设置 1 个种子，5M 步，128 个世界）

replay、cat、fair、fair_valid 四个模型，设置都一样（种子 0，导航观测）。评测在 100 个测试场景上进行，确定性动作。

- **评测脚本：** `scripts/gpucat/evaluate.py` 逐场景记录结果，`logs/gpucat/eval/<run>.csv` 和训练里最后一次评测完全一致。
- **比较脚本：** `scripts/gpucat/compare_runs.py` 在同一批场景上逐对比较：bootstrap 95% 置信区间，以及 McNemar 精确检验。结果在 `logs/gpucat/eval/compare.md`。

**最后 5 次评测（3.3M–5.0M 步）的平均：**

| 训练 | 无对手：到达 / 碰撞 / 出界 / 完成度 | CAT 对手：到达 / 碰撞 / 出界 / 完成度 | fair 对手：到达 / 碰撞 / 出界 / 完成度 |
|---|---|---|---|
| replay | 0.45 / 0.29 / 0.23 / 0.68 | 0.37 / 0.42 / 0.20 / 0.65 | 0.43 / 0.32 / 0.22 / 0.67 |
| cat | 0.47 / 0.30 / 0.21 / 0.69 | 0.40 / 0.39 / 0.20 / 0.66 | 0.44 / 0.33 / 0.22 / 0.68 |
| fair | 0.46 / 0.31 / 0.20 / 0.70 | 0.39 / 0.39 / 0.20 / 0.66 | 0.46 / 0.31 / 0.21 / 0.69 |
| fair_valid | 0.47 / 0.26 / 0.25 / 0.68 | 0.37 / 0.36 / 0.25 / 0.64 | 0.44 / 0.29 / 0.25 / 0.67 |

同一检查点前后几次评测的标准差是 1–4 pp。

**配对比较（最终模型）：**
- **fair 对 cat：** 无对手时，路线完成度 +1.5 pp，95% CI [−3.8, +7.0]；CAT 对手下 −0.3 pp，CI [−6.3, +5.4]。MetaDrive 上的 +10 pp 和 +14.7 pp 都落在置信区间之外，所以**没有复现**。
- **cat 对 replay：** CAT 对手下，碰撞率 −4 pp，CI [−12, +4]；路线完成度 +4.0 pp，CI [−1.4, +9.2]。都不显著，和 MetaDrive 一样。
- **fair_valid：** 碰撞少 3–7 pp，出界多 3–5 pp，到达率不变。CAT 对手下，路线完成度比 cat 低 5.9 pp（CI [−11.6, −0.1]），这是唯一一个置信区间不含 0 的差异。

**对手在训练中是起作用的：**
- 后半段约 90% 的训练回合有对手。训练回合的碰撞率：cat 0.29、fair 0.25、fair_valid 0.25，replay 是 0.20。
- 对手对测试的影响：replay 模型从无对手换成 CAT 对手，碰撞率从 0.28 升到 0.42，增加 14 pp。MetaDrive 上的 TD3 replay 是从 21% 升到 42%，增加 21 pp。

**结论：** 在 GPUDrive + PPO 上，无论用 CAT 的对手还是 fair 的对手训练，测试表现都和只回放日志训练没有可测的区别。即使没有对手，也有 26–31% 的回合以碰撞结束：背景交通按日志回放，不会对自车做出反应。所以对手带来的那部分碰撞不是主要的失败来源。
